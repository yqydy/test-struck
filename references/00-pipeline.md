# 00 · 一条统一的项目流水线

这份手册把三个仓库合成为一条可执行路径：

```
判断（Awesome-Architecture） → 造智能（Hello-Agents） → 做产品（Easy-Vibe）
架构与取舍                        Agent 与评测                  原型、全栈与上线
```

它不是“先读 90 章再开始”。做项目时，按下面的阶段取用，缺哪块补哪块。

## 六阶段流水线

| 阶段 | 要回答的问题 | 产物 | 通过条件 | 主要参考 |
|---|---|---|---|---|
| **0 · Frame** | 为谁、解决什么、不做什么、成功怎么量？ | 项目简报（1 页） | 用户、指标、非目标、约束都说清楚 | `templates/project-brief.md` |
| **1 · Architecture** | 系统该长什么样，为什么不是别的样子？ | 架构草图（C4 L1/L2）、取舍表、ADR | 数据源、边界、失败模式、回滚都有答案 | `01-architecture-playbook.md` |
| **2 · AI shape** | 真的需要 AI / Agent 吗？用哪种形态？ | Agent 规格或“不需要 Agent”的结论 | AI 有明确工作、工具、停止条件和评测 | `02-agent-playbook.md` |
| **3 · Prove** | 最小可验证的一条路径是什么？ | 可点击原型或纵向切片 | 用户能完成一个真实任务，指标可观测 | `03-delivery-playbook.md` |
| **4 · Harden** | 真实用户、数据、钱进来后会先死在哪？ | 评测集、限流/重试/幂等、可观测性、回滚 | 关键失败有兜底，AI 有回归门禁 | `01` + `02` + `templates/eval-plan.md` |
| **5 · Ship & learn** | 怎么上线、怎么收款、怎么知道该不该继续？ | 上线清单、监控面板、复盘 | 有指标、有反馈、有演进触发信号 | `03-delivery-playbook.md` |

### 阶段 0 · Frame

不要先问“用什么框架”。先写：

- 一个用户、一个场景、一个可观察结果；
- 成功指标（时间、成本、转化、准确率、满意度）；
- 非目标（明确不做什么）；
- 关键约束：规模、延迟、一致性、预算、合规、团队能力；
- 当前替代方案：用户今天怎么解决？为什么现有方案不够？

如果这些问题无法回答，不要进入实现。先做 3–5 次用户访谈或手工模拟。

### 阶段 1 · Architecture

用 `01-architecture-playbook.md` 的 8 步法。最小产物：

1. 规模信封（DAU、峰值 QPS、数据量、延迟、成本）；
2. 数据源与一致性模型；
3. 同步/异步边界与 API 契约；
4. 一张 C4 图；
5. 失败模式、爆炸半径与回滚；
6. 1–3 条 ADR。

### 阶段 2 · AI shape

按 `02-agent-playbook.md` 的决策表判断：

- 步骤确定 → 代码/工作流，不要 Agent；
- 一次转换 → 单次 LLM 调用；
- 动态规划 + 工具 + 环境反馈 → Agent；
- 多 Agent 只有在专业化、并行或独立验证带来可量测收益时才用。

AI 不是默认答案；能不用就不用，必须用时再选最小形态。

### 阶段 3 · Prove

“纵向切片”必须端到端：

```
用户操作 → UI → API → 数据/鉴权 → LLM/工具（可先 mock） → 结果 → 日志/指标
```

切片的目标不是炫技，而是验证：
- 用户是否愿意完成这个任务；
- 数据/权限/成本是否可行；
- 哪个假设最可能错。

### 阶段 4 · Harden

这是 Demo 与生产之间的分水岭。最低限度：

- 超时、重试、幂等、限流、降级；
- 鉴权、租户隔离、密钥管理；
- 日志、指标、告警、成本；
- AI 评测集与回归门禁；
- 数据备份、迁移、回滚；
- 人工审批/沙箱（涉及工具与副作用时）。

### 阶段 5 · Ship & learn

上线不是终点。至少要能回答：

- 用户有没有完成核心任务？
- 失败最多的前三类是什么？
- 单次请求/单用户成本是多少？
- 哪个指标触发“继续投入 / 简化 / 回滚”？

## 模式选择

不要对每个请求都跑完整流水线：

| 模式 | 典型时长 | 最低产物 |
|---|---|---|
| M0 快速任务 | 几小时 | 验收条件 + 变更 + 冒烟验证 |
| M1 MVP | 几天 | 简报 + 架构草图 + 一个切片 + 演示 |
| M2 生产 | 几周 | 全量架构、ADR、评测、加固清单 |
| M3 Agent 功能 | 任意 | Agent 规格 + 工具合同 + 评测集 |
| M4 评审 | 几小时 | 按严重级别排序的 findings |
| M5 架构设计 | 几小时/几天 | 决策备忘录 + 图 + 选项/取舍 |

**模式可以组合，不要单选后漏步骤。**

- **M1 + M3（MVP 带 AI）**：`00 → 01 → 02 → 03`。先写项目简报和架构草图，再写 Agent 规格与评测，最后做切片。不要先做 Agent 再补架构；否则数据、权限、失败模式和成本都会返工。
- **M2 + M3（生产 Agent）**：在 M1+M3 的切片之后，补评测门禁、可观测性、安全、限流、回滚和 runbook。
- **M4 评审**：不接管实现；输出 findings 和最小修复，不自动重写整个系统。

## 项目事实源

建议项目里保留这些文件（命名可调整）：

```
docs/
  project-brief.md       # 为什么做、为谁做、怎么算成功
  architecture.md        # 当前架构、边界、数据流
  decisions/             # ADR-0001.md ...
  agents/                # agent 规格、工具合同
  evals/                 # 评测集、失败案例、阈值
  runbook.md             # 部署、回滚、告警、值班
```

如果项目很小，至少保留一个 `README` 里的“目标 / 非目标 / 运行 / 验证 / 已知风险”区块。

## 什么时候回退

出现下列信号时，不要继续加功能：

- 核心用户任务完成率下降；
- 每次改 prompt/模型都靠肉眼回归；
- 成本或延迟超过预算 2 倍；
- 数据不一致需要人工对账；
- 故障恢复依赖某个人记忆；
- 团队开始用“以后再说”解释安全和权限问题。

回退到上一个阶段：先修评测/架构/范围，再继续。
