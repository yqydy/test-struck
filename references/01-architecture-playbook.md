# 01 · 架构判断手册

> 来源主线：Awesome-Architecture 的“需求 → 约束 → 质量属性 → 取舍”，C4，ADR，以及分布式、演进、AI 时代章节。
> 用法：任何新系统、重大功能、架构评审、技术选型都先走这一遍；小任务可只做“精简版”。

## 什么时候必须做架构判断

- 新系统、新服务、新数据库、新消息通道；
- 需求里有“实时、强一致、多租户、支付、大规模、合规”等词；
- 引入 AI/Agent，涉及非确定性、工具副作用、上下文与成本；
- 现有系统要拆、要迁移、要换技术栈；
- 代码评审发现“能跑，但说不清为什么这样设计”。

小改动可以跳过完整流程，但至少写清：改什么、影响谁、失败怎么回滚。

## 8 步设计法

### 1. 澄清范围与结果

写下：

- 一个主要用户/角色；
- 一个核心任务；
- 可观察结果与成功指标；
- 非目标；
- 当前替代方案；
- 不做的后果。

输出：**项目简报**（`templates/project-brief.md`）。

### 2. 建立规模信封

不要精确预测，只要有数量级：

| 维度 | 例子 | 影响 |
|---|---|---|
| 用户/租户 | 100 内部用户 / 10 万 C 端 | 鉴权、隔离、缓存 |
| 峰值 QPS | 10 / 1,000 / 100,000 | 架构、队列、限流 |
| 数据量/增长 | 10 GB/年 / 10 TB/天 | 存储、索引、分区 |
| 延迟目标 | p95 < 200 ms / < 2 s | 同步/异步、缓存 |
| 可用性 | 99% / 99.9% / 99.99% | 冗余、多活、成本 |
| 成本上限 | 每请求 ¥0.01 / 每用户 ¥1/月 | 模型选择、缓存、降级 |
| 峰值系数 | 日常 1x，活动 20x | 容量、排队、降载 |

把这些写成假设；上线后用真实数据替换。

### 3. 选择 3 个主质量属性

质量属性互相冲突。不要全都要，选 3 个优先级最高的：

| 质量属性 | 典型问题 | 代价 |
|---|---|---|
| 性能/延迟 | 用户能等多久？ | 缓存、预计算、更贵资源 |
| 可用性/韧性 | 挂了会怎样？ | 冗余、降级、复杂度 |
| 一致性 | 数据错了会赔钱吗？ | 事务、锁、协调、延迟 |
| 成本 | 单位经济模型撑得住吗？ | 缓存、批处理、更慢但更便宜 |
| 安全/隐私 | 最坏泄露是什么？ | 隔离、加密、审计、审批 |
| 可运维性 | 谁能值班、怎么回滚？ | 标准化、可观测、发布流程 |
| 可演进性 | 半年后怎么改？ | 模块化、抽象、测试 |

**取舍要写成“拿什么换什么”**，例如：

> 为了把 p95 从 2s 降到 300ms，接受读模型最终一致（秒级），并用 Outbox 保证不丢事件。

### 4. 数据与状态

先画数据生命周期：产生 → 存储 → 读取 → 更新 → 删除/归档。

必须明确：

- **事实源（source of truth）** 是哪个存储？
- 哪些是派生读模型/索引/缓存？
- 一致性模型：强一致、读己之写、最终一致？
- 事务边界在哪里？
- 幂等键是什么？
- 删除/隐私请求怎么传播？

常见分工：

| 需求 | 优先选择 |
|---|---|
| 交易、权限、账务 | 关系型数据库 + 事务 |
| 高并发点查 | KV/文档 + 缓存 |
| 全文/相关性检索 | 搜索引擎（倒排索引） |
| 语义检索 | 向量索引 + 混合检索 + 重排 |
| 大文件/媒体 | 对象存储 + CDN |
| 异步解耦/削峰 | 消息队列/事件流 |

不要把向量库当事实源；不要把缓存当账本。

### 5. API 与服务边界

按“变化频率”和“所有权”切边界，而不是按技术层切。

每个边界写清：

- 谁拥有数据？
- 同步还是异步？
- 契约（请求/响应/错误码/版本）；
- 超时、重试、幂等；
- 鉴权与租户；
- 失败时的用户可见行为。

优先：

- 模块化单体；
- 清晰模块边界；
- 进程内调用；
- 单数据库 + schema 隔离。

只有在独立扩缩、独立发布、独立团队/合规边界真正需要时，才拆服务。

### 6. 画架构图（C4 L1/L2）

至少两张：

- **L1 系统上下文**：用户、外部系统、你的系统。
- **L2 容器**：Web/API/Worker/DB/队列/对象存储/模型/工具。

图不是装饰。每根箭头都要能回答：

- 数据是什么？
- 同步还是异步？
- 失败会怎样？
- 谁重试？
- 有没有幂等？

### 7. 失败、安全与 AI 约束

逐项过：

| 失败 | 设计动作 |
|---|---|
| 上游超时 | 超时预算、重试退避、熔断、降级 |
| 重复请求 | 幂等键、去重表、唯一约束 |
| 消息丢失/重复 | Outbox、至少一次 + 幂等消费 |
| 流量尖峰 | 限流、排队、舱壁、降载 |
| 数据损坏 | 备份、校验、恢复演练 |
| 越权/租户串数据 | 每查询强制 tenant 过滤、行级安全 |
| 提示注入/工具滥用 | 工具白名单、沙箱、人工审批、输出校验 |
| 模型/供应商变更 | 固定版本、评测门禁、fallback |

AI 时代新增三个一等约束：

1. **非确定性**：同一输入可能不同输出；必须用评测与置信度/拒绝策略，而不是断言唯一答案。
2. **上下文工程**：上下文窗口是预算；稳定前缀、压缩、结构化状态、检索比“塞更多”更重要。
3. **成本/延迟/质量三角**：换模型、加检索、加反思都会改变三者；必须量化。

### 8. ADR 与演进触发

每个重要决策写一条 ADR（`templates/adr.md`）：

- 背景与约束；
- 决策；
- 备选方案；
- 代价与后果；
- 复审条件/触发信号。

演进触发信号示例（按项目改写）：

- p95 延迟连续一周 > 目标 1.5 倍；
- 队列积压 > 5 分钟；
- 单租户数据量导致索引退化；
- 单库写入接近上限；
- 团队 > 2 个小组同时改同一模块；
- 发布频率/回滚次数明显上升；
- 单请求成本超过毛利可承受范围。

没有触发信号，就不要为了“先进”提前拆架构。

## 常见取舍卡

| 选择 | 适合 | 不适合 |
|---|---|---|
| 模块化单体 | 大多数 MVP 和中小系统 | 独立扩缩/独立团队边界已真实存在 |
| 微服务 | 明确服务边界、独立团队/扩缩 | 为了“看起来专业” |
| 事件驱动 | 异步解耦、削峰、广播 | 需要强一致、链路可观测性不足 |
| CQRS | 读写差异大、复杂查询 | 简单 CRUD |
| 缓存 | 读热点、昂贵计算 | 强一致账务/库存扣减 |
| 向量检索 | 语义召回 | 精确过滤、账务、权限判断 |
| 长上下文 | 少量长文档、快速原型 | 大规模知识库、成本敏感 |
| 微调 | 稳定风格/格式、数据充足 | 先于 prompt/RAG/eval 的“银弹” |
| 多 Agent | 专业化、并行、独立验证 | 单 Agent + 工具就能完成 |

## 架构评审清单

- [ ] 用户、结果、非目标、规模信封有文字。
- [ ] 3 个主质量属性明确，冲突有取舍记录。
- [ ] 数据事实源、一致性、幂等、删除路径明确。
- [ ] 同步/异步边界和错误语义明确。
- [ ] C4 图能解释数据流和故障流。
- [ ] 至少一个失败模式有降级/回滚方案。
- [ ] 鉴权、租户隔离、密钥、审计有归属。
- [ ] 可观测性：日志、指标、追踪、告警、成本。
- [ ] 迁移/备份/恢复/回滚经过演练或有明确计划。
- [ ] 至少一条 ADR 记录了“为什么不选另一个方案”。
- [ ] AI 功能有评测、成本上限、人工兜底/拒绝策略。

## 反模式

- 先选技术，再找理由。
- 把所有“最佳实践”都加上，没有主质量属性。
- 用微服务解决代码组织问题。
- 把缓存、搜索索引、向量库当事实源。
- 忽略删除、隐私、租户隔离，直到上线。
- 没有回滚的数据库迁移。
- 把 Demo 的性能/成本当生产数据。
- 用“以后加监控/评测”结束设计。
