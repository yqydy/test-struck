# 03 · 产品交付手册

> 来源主线：Easy-Vibe 的 Stage 1（原型）→ Stage 2（全栈与上线）→ Stage 3（AI 原生与跨端），以及附录中的工程基础。
> 用法：从“想法”走到“用户能用、愿意付费、能维护”的产品时使用；纯架构/纯 agent 任务可以只读相关小节。

## 1. 先验证问题，再做产品

至少回答：

- 用户在什么场景遇到什么问题？
- 今天怎么解决？成本/体验如何？
- 为什么现有方案不够？是频率、成本、体验、合规还是能力缺口？
- 谁会为它付费/推动采购？
- 你如何在 1–2 周内验证最危险的假设？

用户访谈原则：

- 问过去发生的事，不问“你会不会用”；
- 问具体流程、时间、钱、替代方案；
- 不要向用户推销你的方案；
- 记录原话，不记录你的解释；
- 用可点击原型/服务替代“口头描述”。

## 2. 定义 MVP

MVP 不是“功能少”，而是**最小可验证闭环**：

- 一个用户/角色；
- 一个核心任务；
- 一条 happy path；
- 一个可观测指标；
- 明确非目标。

示例：

> 给 20 人内部客服团队：把“查文档 → 草拟回复 → 人工确认”做成一个页面；非目标：自动退款、全渠道接入、复杂权限。

## 3. 先做可演示原型

顺序：

1. 线框/流程（Figma、纸面、HTML）；
2. 可点击 UI（真实交互，假数据/假模型）；
3. 接一个真实模型或 API；
4. 找 3–5 个目标用户完成任务；
5. 记录失败点，再决定是否进入全栈。

原型阶段允许 vibe coding；生产阶段要 spec-first。区分标准：

- 只用来学习/演示？快速迭代。
- 会接触真实用户/数据/钱？先写规格、权限、回滚。

## 4. 全栈装配顺序

从薄到厚：

1. **UI**：核心页面 + 状态（空/加载/错误/成功）。
2. **API**：请求/响应/错误码/超时/鉴权。
3. **DB**：事实源、表/索引、迁移、备份。
4. **Auth**：登录、会话、角色、租户。
5. **文件/媒体**：对象存储、上传限制、病毒/类型检查。
6. **支付**：商品、结算、webhook、幂等、对账。
7. **管理后台**：用户/内容/工单/审计。
8. **部署**：环境、域名、证书、密钥、日志。
9. **可观测**：错误、指标、追踪、告警。
10. **运营**：条款、隐私、支持、AI 披露。

不要先做“完美架构”再做第一条路径；也不要跳过鉴权和迁移。

## 5. 技术栈选择（MVP 默认值）

这些是默认起点，不是教条：

| 层 | 默认 | 何时升级 |
|---|---|---|
| 前端 | React/Next.js 或 Vue/Nuxt | 需要复杂客户端状态/离线/跨端 |
| 后端 | 单体 API（Node/Python/Go 任一） | 独立扩缩/团队边界出现 |
| 数据库 | Postgres | 极端写入/时序/搜索需求 |
| 鉴权 | Supabase/Auth.js/Clerk 等托管 | 企业 SSO/复杂权限 |
| 文件 | S3 兼容对象存储 | 超大文件/处理流水线 |
| 部署 | Vercel/Zeabur/Cloudflare/Render | 需要 VPC/K8s/合规隔离 |
| 支付 | Stripe（或目标市场等价物） | 多币种/订阅/对账复杂 |
| 观测 | 托管日志 + 错误追踪 + 基础指标 | SLO/值班/审计 |

原则：**先买/托管，后自建**；先单区域，后多活；先单体，后拆分。

## 6. 支付与资金路径

- 测试模式跑通全链路，再切生产；
- 价格、币种、税、退款政策先定；
- 支付成功以 **webhook + 主动查询** 双重确认；
- 订单/支付/权益各自状态机，幂等键；
- 处理重复回调、乱序、失败重试；
- 每日/每月对账，异常告警；
- 不把“前端跳转成功”当支付成功。

## 7. AI 功能接入

- 先做 fallback：模型失败/超时/超预算时的 UI 与行为；
- 流式输出要有终止、重试、取消；
- 用户输入/文档内容视为不可信；
- 记录模型、prompt 版本、token、成本、延迟；
- 对用户展示引用/依据（RAG）；
- 上线前做评测与红队（见 `02-agent-playbook.md`）。

## 8. 部署与上线清单

### 上线前

- [ ] 环境变量/密钥不在仓库；生产/测试隔离。
- [ ] 数据库迁移可前滚、可回滚；已备份。
- [ ] 域名、HTTPS、重定向、SEO（如需要）。
- [ ] 鉴权/租户隔离测试。
- [ ] 关键路径有错误/空/加载状态。
- [ ] 限流、超时、重试、幂等。
- [ ] 日志、错误追踪、基础指标、告警接收人。
- [ ] 备份/恢复演练。
- [ ] 支付测试模式 & 生产模式验证。
- [ ] 条款/隐私/AI 披露/联系方式。
- [ ] 回滚步骤写在 runbook。
- [ ] 成本上限与预算告警。

### 上线后

- [ ] 核心漏斗/任务完成率。
- [ ] 错误率、p95 延迟、模型失败率。
- [ ] 单用户/单请求成本。
- [ ] 用户反馈与失败样本进入评测集。
- [ ] 每周复盘：继续、简化、回滚。

## 9. 跨端选择

| 形态 | 适合 | 注意 |
|---|---|---|
| Web | 大多数 MVP、SEO、后台 | 浏览器兼容、响应式 |
| PWA | 移动 Web、轻量离线 | iOS 限制、推送 |
| 微信小程序 | 国内微信生态、线下扫码 | 审核、域名、支付 |
| 原生 Android/iOS | 深度系统能力、应用商店 | 双端成本、审核 |
| React Native/Expo | 双端复用、快速迭代 | 原生模块边界 |
| Flutter | 高度定制 UI、多端 | Dart 生态/包体积 |
| Electron/Tauri | 桌面工具、本地文件 | 签名、更新、体积 |
| 浏览器扩展 | 网页增强、轻量入口 | 商店审核、权限 |
| Qt | 工业/桌面/硬件 | 授权、部署 |

先选“用户已经在那里”的形态，不要为了跨端而跨端。

## 10. AI 辅助开发工作流

- **探索/原型**：vibe coding，快速对话迭代；
- **生产**：spec-first；先写清目标、约束、接口、验收，再让 AI 实现；
- 任务拆小：一个 PR 一个可验证结果；
- 让 AI 先读现有代码/规范；给上下文，不只给结论；
- 审查 AI 产出：超时、重试、幂等、权限、错误处理、测试缺什么；
- 用 lint/typecheck/test/构建作为硬门禁；
- 重要决策写 ADR，不藏在聊天记录里；
- 用 CI 保护主分支，不直接让 AI 推生产。
