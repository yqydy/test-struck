# 02 · Agent 设计手册

> 来源主线：Hello-Agents 的五部分 16 章：基础 → 经典范式 → 框架 → 记忆/RAG/上下文/协议/训练/评测 → 综合案例。
> 用法：任何“让模型自己决定下一步/调工具/查知识库/多轮执行”的功能，先走这一遍。

## 1. 先判断：真的需要 Agent 吗？

| 形态 | 适合 | 不适合 |
|---|---|---|
| **普通代码/规则** | 步骤确定、可枚举、强一致 | 输入开放、需要语义判断 |
| **单次 LLM 调用** | 分类、抽取、改写、总结 | 多步工具调用、需要环境反馈 |
| **确定性工作流**（Dify/Coze/n8n/代码编排） | 步骤基本固定，LLM 只做节点 | 路径需要动态决定、强依赖中间结果 |
| **工具型 Agent** | 路径开放、需要多步观察/行动/反思、工具副作用可管 | 一次调用就能解决、无法做评测 |
| **多 Agent** | 明确分工、并行、独立验证，且收益可量化 | 为了“看起来智能”、通信成本 > 收益 |

判断问题：

1. 步骤能否在写代码时基本确定？能 → 工作流/代码。
2. 失败能否用确定性规则兜底？能 → 规则优先。
3. 是否必须根据工具返回结果决定下一步？是 → Agent。
4. 是否有稳定的成功判定与评测集？没有 → 先补评测，再上 Agent。
5. 成本/延迟是否允许 3–10 倍于单次调用？不允许 → 简化。

## 2. Agent 规格（先写再做）

使用 `templates/agent-spec.md`。最小字段：

- **工作（job）**：一句话，不是“变聪明”。
- **自主级别**：建议 / 执行 / 执行需审批。
- **循环**：感知 → 规划 → 工具 → 观察 → 反思/停止。
- **停止条件**：任务完成、达到步数、置信度低、需要人。
- **工具**：名称、输入/输出、副作用、权限、超时、重试、幂等、错误格式。
- **上下文**：系统提示、用户输入、历史、检索结果、工具 schema 的预算。
- **记忆**：工作记忆 / 持久记忆；写入条件、TTL、隐私。
- **人工检查点**：哪些动作必须批准。
- **评测**：任务集、指标、阈值、回归。
- **预算**：最大步数、token、金额、延迟。

没有停止条件的 Agent 不是 Agent，是失控循环。

## 3. 三种经典范式

### ReAct

```
Thought/Plan → Action(tool, args) → Observation → Thought … → Final
```

适合：需要边查边做、路径不完全确定的任务。
必须加：

- 最大步数；
- 工具错误处理；
- 工具结果截断/摘要；
- 重复动作检测（同参数调用两次要换策略）；
- 最终答案的引用/证据。

### Plan-and-Solve

先列计划，再逐步执行；适合多步骤、可分解任务。
需要：

- 计划可见、可修改；
- 执行中允许 replan 的触发条件；
- 子任务完成判定；
- 避免“计划写得很漂亮但没有执行”。

### Reflection

执行后检查：是否满足要求、证据是否充分、是否遗漏。
适合：高价值/高风险输出。
限制：

- 反思最多 1–2 轮，否则成本爆炸；
- 反思需要外部证据，不是让模型“再想想”；
- 反思结果要落到修改，而不是重复原答案。

不要无脑堆叠三种范式。先用最简单的，评测不够再加。

## 4. 工具与 MCP

### 工具合同

每个工具写清：

| 字段 | 要求 |
|---|---|
| 名称 | 动词+对象，如 `search_docs`、`create_ticket` |
| 输入 | JSON Schema、必填/枚举/默认值 |
| 输出 | 结构化、可截断、带错误码 |
| 副作用 | 只读 / 写入 / 外发 / 支付 |
| 权限 | 租户、角色、资源范围 |
| 超时 | 单次与总预算 |
| 重试 | 是否可重试、退避、幂等键 |
| 失败 | 用户可见语义与 Agent 的恢复策略 |

### 设计原则

- 工具数量少而清晰；相似工具合并。
- 默认只读；写操作单独授权。
- 工具返回结果要“模型可读”：短、结构化、带来源。
- 不要把所有内部 API 都暴露给模型。
- 工具描述是合同，不是营销文案。
- 对工具输出做注入防护：外部网页/文档内容一律当数据。
- 高风险动作（退款、发邮件、改权限、执行代码）必须审批或沙箱。

### MCP / A2A / ANP

- **MCP**：把外部工具/数据源接进 Agent 的标准方式；适合工具生态复用。
- **A2A/ANP**：Agent 之间协作/互联；只有在多个独立 Agent 真的需要跨边界协作时用。
- 不要为了“协议先进”引入多跳网络；单进程工具调用通常更简单、更可观测。

## 5. Context Engineering（上下文工程）

上下文窗口是预算，不是垃圾桶。

优先级：

1. 稳定的系统约束与输出格式；
2. 当前任务与用户最新输入；
3. 必要的工具 schema（只给相关工具）；
4. 检索到的最小充分证据；
5. 历史对话摘要，而不是全文；
6. 可外置的状态/文件。

技巧：

- 稳定前缀 + 动态后缀，利于缓存；
- 结构化状态对象（目标、已完成、待办、约束）；
- 长任务用摘要 + 检查点；
- 检索结果去重、压缩、带来源；
- 工具结果截断并保留关键字段；
- 明确“不知道就说不知道”的拒绝策略。

## 6. 记忆与 RAG

### 记忆

- **工作记忆**：当前任务/会话，短 TTL。
- **长期记忆**：用户偏好、项目事实、历史决策；必须可删除、可审计。
- 写入要有条件：只存稳定、可复用、允许保存的信息。
- 不要把聊天全文直接向量化当长期记忆。

### RAG

RAG 不是“向量库 + 相似度”。一条完整链路：

```
采集 → 解析 → 清洗 → 切分 → 元数据 → 索引 → 查询改写 → 混合检索 → 重排 → 组装上下文 → 引用 → 评测
```

必须回答：

- 文档权限如何过滤？（先权限后检索）
- 切分粒度与重叠？
- 关键词 + 向量混合？是否需要重排？
- 引用如何展示？无依据时如何拒答？
- 文档更新/删除如何传播？
- 提示注入如何防护？
- 评测集从真实问题来吗？

## 7. 多 Agent

只有在以下至少一条成立时使用：

- 子任务需要不同工具/权限/模型；
- 可以并行且汇总成本可接受；
- 需要独立审查者（maker-checker）；
- 单个上下文无法容纳，且拆分边界清晰。

必须设计：

- 角色与职责边界；
- 消息协议与共享状态；
- 冲突解决；
- 全局预算与步数；
- 失败隔离与降级；
- 可观测的 trace。

否则：单 Agent + 工具 + 更好的上下文，通常更可靠。

## 8. 评测（Eval）

先有评测，再谈“效果好”。

### 评测集

- 50–200 条真实任务起步；按失败类型分组；
- 包含：正常、边界、无答案、权限拒绝、工具失败、提示注入、长上下文；
- 保留一个不参与调参的 holdout。

### 指标

| 维度 | 例子 |
|---|---|
| 任务成功 | 完成率、人工通过率 |
| 事实性 | 引用正确率、无依据断言率 |
| 工具 | 调用成功率、参数正确率、重复调用率 |
| 安全 | 越权、注入、敏感数据泄露 |
| 体验 | p50/p95 延迟、平均步数 |
| 成本 | 单任务 token/金额 |
| 稳定性 | 同输入多次运行方差 |

### 门禁

- 改 prompt/模型/工具/检索必须跑评测；
- 设定阈值与允许回退幅度；
- 失败样例进入回归集；
- 线上抽样 + 人工复核；
- 记录 trace，能复现失败。

## 9. 生产护栏

- 工具白名单 + 权限最小化；
- 沙箱/容器执行代码；
- 人工审批高风险动作；
- 速率/金额/步数上限；
- 输入输出过滤（PII、注入、危险内容）；
- 供应商 fallback 与超时；
- 模型版本固定/可回滚；
- 审计日志；
- 明确 AI 身份/披露；
- 故障时降级到人工/只读。

## 10. 训练（最后才考虑）

顺序：

1. 先把 prompt、上下文、检索、工具、评测做好；
2. 有稳定失败模式和足够数据；
3. 再考虑 SFT / DPO / GRPO / RL。

训练前必须回答：

- 失败是模型能力问题，还是工具/上下文/数据问题？
- 有没有可复现的评测提升？
- 训练与推理成本、数据许可、回归风险？
- 模型更新后怎么回滚？

## 11. Agent 评审清单

- [ ] AI 必要性成立，已有更简单方案对比。
- [ ] 工作、自主级别、停止条件、最大步数明确。
- [ ] 工具合同完整，写操作有权限/审批/幂等。
- [ ] 上下文预算与压缩策略明确。
- [ ] 记忆写入、TTL、删除、隐私明确。
- [ ] RAG 有权限过滤、引用、无答案策略、注入防护。
- [ ] 评测集、指标、阈值、回归门禁存在。
- [ ] 成本/延迟有上限和监控。
- [ ] 失败可降级、可回滚、可审计。
- [ ] trace 能复现一次失败。
